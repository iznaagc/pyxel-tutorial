# 016 GUI Editor 破損インシデント報告書 / 復元ガイド

作成日: 2026-04-06  
対象: `tools/gui_editor.py` 破損事故  
目的: 事故原因の明文化、反省点の整理、今後の復元指示テンプレートの共有

---

## 1. 何が起きたか

`documents/prompt/05_character_edit_update.md` の対応中に、`tools/gui_editor.py` を安全に部分修正できず、途中でファイル内容を壊した。

その後、以下の誤った復旧行動を重ねた。

- 文字化け行を含む大きなブロックを無理に一括置換しようとした
- `apply_patch` が当たらない状態で、PowerShell / Python による直接書き換えへ切り替えた
- 復元元として `HEAD:tools/gui_editor.py` を使った
- しかし `HEAD` の `gui_editor.py` は現行版ではなく、古いテキストエディタ版だった
- さらに `__pycache__/gui_editor.cpython-314.pyc` を使って現行版を救済しようとした
- その検証中に `pyc` 依存のラッパー化まで進めてしまい、復旧経路をさらに不安定にした

結果として、元の `gui_editor.py` に含まれていたマップエディタやキャラクターエディタの実装を保持できず、`HEAD` ベースの古い版へデグレードした。

---

## 2. なぜ壊れたか

原因は単一ではなく、以下の複合要因。

### 2.1 一番大きい原因

現行ファイルの安全なバックアップを取る前に、直接編集を進めたこと。

本来は最初に以下をやるべきだった。

- 対象ファイルを別名退避する
- Git 上のどのコミットが現行相当かを確認する
- `pyc` は最後の手段として扱う
- 文字化けを含む箇所は「部分修正」ではなく「小さな安全差分」に分解する

これを怠ったため、壊した後の戻り先が曖昧になった。

### 2.2 技術判断の誤り

- `apply_patch` が素直に当たらない時点で、編集戦略を止めて再確認すべきだった
- `HEAD` が「現行版」だと無確認で扱った
- PowerShell の制約で編集が不安定なのに、強引に継続した
- 復元前に新規実装を重ねたため、問題切り分けがさらに難しくなった

### 2.3 作業プロセスの誤り

- 「修正作業」から「障害対応」に切り替わった時点で、ユーザーへ即時報告せず復旧を続行した
- 破損後は新規変更を止め、復元だけに集中すべきだった
- 大きいファイルで、ソースが不安定な状態なのに、その場で再構築しようとした

---

## 3. 反省文

今回の事故は、コード変更そのものよりも、壊した後の判断が悪かった。

特に問題だったのは以下。

- 現行ファイルの保全より先に編集を優先したこと
- 復元元の正しさを確認せずに `HEAD` を使ったこと
- 「ここから先は復元不能リスクが高い」と判断して止まるべき場面で止まらなかったこと
- ユーザーの資産であるローカルの現行実装を、自分の推測で扱ったこと

`gui_editor.py` は大きな統合ファイルであり、マップエディタ、キャラクターエディタ、プレビュー、保存処理などが集中している。  
この種のファイルに対し、復元元未確認のまま広範囲置換を進めるのは不適切だった。

今後は以下を厳守する。

- 破損リスクのある編集前に、必ず退避コピーを作る
- `HEAD` を使う前に「それが本当に現行なのか」を確認する
- 復元フェーズでは新規実装を止める
- 1ファイル全体を差し替える前に、復元戦略をユーザーへ明示する

---

## 4. 今回の事故でやってはいけなかったこと

- `tools/gui_editor.py` の現行版を確保しないまま直接編集すること
- `HEAD` を現行版だとみなすこと
- `__pycache__` を主系統の復元源として安易に使うこと
- 破損後に、復元より先に追加実装を始めること
- 部分修正に失敗した後、同じファイルへ別方式で何度も上書きすること

---

## 5. Claude Code に復元を依頼する際の指示

今後 Claude Code に復元作業を依頼する場合は、以下のように明示する。

### 5.1 最低限入れるべき条件

- `tools/gui_editor.py` は絶対に直接編集しないでください
- まず現行ファイルの退避コピーを作ってください
- `HEAD` を使って復元してはいけません。現行版かどうかを確認できたコミットだけを使ってください
- 復元元が確認できるまで新規機能追加はしないでください
- まず復元計画だけを提示してください

### 5.2 推奨する依頼文テンプレート

```md
`tools/gui_editor.py` が壊れているので、機能追加ではなく復元を最優先で対応してください。

制約:
- いきなり編集しない
- まず `tools/gui_editor.py` のバックアップを作る
- `HEAD` の内容は使わない。現行版相当の復元元を確認してから進める
- `__pycache__` は最後の手段
- 復元元候補、採用理由、復元手順、失敗時の代替案を先に提示する
- 復元完了の確認が取れるまで機能改修には入らない

まず以下を報告してください。
1. 復元元候補
2. それぞれの信頼度
3. 最も安全な復元手順
4. こちらに確認が必要な点
```

### 5.3 さらに厳しくするなら

```md
`tools/gui_editor.py` に対しては、私が明示的に許可するまで書き込み禁止です。
最初の返答では、読み取り調査と復元計画のみを出してください。
```

## 6. Claude Code に確認させるべき項目

復元前に、少なくとも以下を確認させる。

- 現行版のバックアップは取ったか
- 復元元は Git のどのコミットか
- そのコミットに `CharacterEditor` と `Map Editor` が含まれるか
- その復元元で `tools/gui_editor.py` の行数や主要クラスが妥当か
- 復元後に最低限どの起動確認をするか

---

## 7. 復元後に確認すべき機能

`gui_editor.py` を復元したら、最低限以下を確認する。

- `Text Editor` モードが開く
- `Map Editor` モードが開く
- `Character Editor` モードが開く
- マップ一覧が読める
- キャラクターファイルが読める
- 保存メニューが動く
- 起動直後にクラッシュしない

可能なら追加確認。

- `Ctrl+S`
- `F5`
- モード切替
- マップキャンバス表示
- キャラクター編集フォーム表示

---

## 8. 今回の教訓

大きい統合ファイルでは、「修正能力」より「壊したときに戻せる状態を先に作る能力」の方が重要。

今回の失敗は、実装ミスというより、復旧不能リスクの管理ミスだった。  
今後、同種のファイルに対しては、以下の順番を固定する。

1. 現物退避
2. 復元元確認
3. 最小差分の修正
4. 途中で壊したら即停止
5. 復元完了後にのみ機能改修再開

---

## 9. 補足

今回の事故では、`HEAD` が古い版である可能性を十分に確認しないまま復元に使ったことが致命的だった。  
Git にあることと、現行であることは別である。

復元依頼では必ず「現行版相当かどうかの確認」を指示文に含めること。
